# ADR-0041: SIMD-Accelerated GF(2^8) Multiply-Accumulate

**Status:** Accepted
**Date:** 2026-03-18

## Context

The RLC window decoder's hot loop is `gf256::mul_acc_slice(coeff, src, dst)`, computing
`dst[i] ^= coeff * src[i]` via scalar log/exp table lookups. Called O(pivots × symbol_size)
times per repair symbol during Gaussian elimination, this is the dominant cost in FEC decoding.

The scalar implementation has three performance bottlenecks:

1. **Unpredictable branch** — `if s != 0` per byte (only 1/256 chance of zero, but
   the branch predictor can't learn the pattern on random payload data)
2. **Two dependent table lookups** per byte — `LOG_TABLE[s]` → `EXP_TABLE[...]`
3. **Modular reduction** — `% 255` generates a division instruction

## Decision

Implement SIMD-accelerated GF(2^8) multiplication using the **split-table PSHUFB** technique
(the same approach used by Intel ISA-L and the Linux kernel RAID6 code).

### Split-table technique

For a coefficient `c`, precompute two 16-entry tables:
- `table_lo[i] = c * i` for `i ∈ [0, 15]` (low nibble products)
- `table_hi[i] = c * (i << 4)` for `i ∈ [0, 15]` (high nibble products)

Then `c * byte = table_lo[byte & 0x0F] ^ table_hi[byte >> 4]`, exploiting the
distributive law: `c * (lo ⊕ hi) = (c * lo) ⊕ (c * hi)` in GF(2^8).

The x86 `pshufb` instruction performs a parallel 16-entry table lookup on all
bytes simultaneously — processing 16 bytes/cycle (SSSE3) or 32 bytes/cycle (AVX2).

### Implementation

- **`gf256/src/simd.rs`** — SSSE3 (16 B/iter) and AVX2 (32 B/iter) kernels for
  `mul_acc`, `mul_slice`, and `xor_acc`, each with safe dispatch wrappers
- **Runtime detection** — `OnceLock<fn(...)>` + `is_x86_feature_detected!` at first call;
  AVX2 preferred over SSSE3, scalar fallback for non-x86
- **Public API unchanged** — `mul_acc_slice` and `mul_slice` signatures identical;
  all unsafe code isolated in `simd.rs`
- **Tail handling** — AVX2 kernels fall through to SSE for 16-byte remainder,
  then scalar for < 16 bytes

### Kernels

| Kernel | Stride | Throughput (theoretical) |
|--------|--------|------------------------|
| Scalar | 1 B | ~0.3 GB/s (2 table lookups + branch/byte) |
| SSSE3 | 16 B | ~5 GB/s (1 pshufb pair/cycle) |
| AVX2 | 32 B | ~10 GB/s (1 vpshufb pair/cycle) |

## Consequences

- **Positive:** ~15-25× speedup on the FEC decode hot path, reducing decode latency
  proportionally for large symbols
- **Positive:** Zero API change — all callers benefit automatically
- **Positive:** All unsafe code contained in one module with safe wrappers
- **Negative:** x86_64-only acceleration; other architectures use scalar fallback
  (ARM NEON `vtbl` variant could be added later)
- **Negative:** `OnceLock` adds one-time detection cost (~ns) on first call
