# Benchmark Methodology

This document describes the simulation model, channel parameters, trial structure,
and interpretive caveats for the raptorpath benchmark suite (`bench_suite.rs`).

---

## 1. Channel Models

All network channels use the **Gilbert-Elliott (GE) two-state Markov model**.
Each packet passes through a loss decision based on the current state, then the
state may transition.

### Steady-state math

Given transition probabilities `p_gb` (Good-to-Bad) and `p_bg` (Bad-to-Good),
and per-state loss probabilities `loss_good` and `loss_bad`:

```
pi_bad        = p_gb / (p_gb + p_bg)
pi_good       = 1 - pi_bad
avg_loss      = pi_good * loss_good + pi_bad * loss_bad
mean_burst    = 1 / p_bg   (expected packets in Bad before returning to Good)
```

### Preset channels

| Channel    | Delay | Jitter | GE(p_gb, p_bg, loss_good, loss_bad) | pi_bad | avg_loss | Burst (pkts) |
|------------|------:|-------:|-------------------------------------|-------:|---------:|-------------:|
| Datacenter |   1ms |    0ms | GE(0.0, 1.0, 0.001, 0.0)           |   0.0% |    0.1%  |          1.0 |
| WiFi       |   5ms |    3ms | GE(0.03, 0.50, 0.01, 0.30)         |   5.7% |    2.6%  |          2.0 |
| LTE        |  20ms |    5ms | GE(0.02, 0.25, 0.005, 0.40)        |   7.4% |    3.4%  |          4.0 |
| Satellite  | 100ms |   10ms | GE(0.05, 0.40, 0.04, 0.50)         |  11.1% |    9.1%  |          2.5 |

**Datacenter** uses `p_gb=0.0`, so the channel never enters the Bad state. All
loss is uniform i.i.d. at 0.1% from `loss_good`. This is a degenerate GE model
equivalent to Bernoulli loss.

### Congested variants

Congested channels layer a `LinkModel` (finite-capacity bottleneck with
tail-drop queue) on top of the base GE channel:

| Variant        | Base    | Capacity | Buffer (pkts) |
|----------------|---------|----------|---------------|
| WiFi congested | WiFi    | 10 Mbps  | 20            |
| LTE congested  | LTE     |  2 Mbps  | 10            |

When the queue is full, additional packets are tail-dropped. There is no AQM
(no RED, no CoDel). The `LinkModel` adds serialization delay
(`pkt_size / capacity`) plus queuing delay to each surviving packet.

### ge_for_target_loss helper

For Table 1b (bursty loss sweep), the `ge_for_target_loss(target, burst_len)`
function derives GE parameters from a desired average loss rate and mean burst
length:

```
loss_good = 0.0
loss_bad  = 0.7
p_bg      = 1.0 / mean_burst_len
pi_bad    = target_loss / loss_bad
p_gb      = pi_bad * p_bg / (1 - pi_bad)
```

This produces a channel where all loss occurs in the Bad state (loss_good=0),
and the Bad state drops 70% of packets. The steady-state fraction `pi_bad` is
chosen so that `pi_bad * 0.7 = target_loss`.

### Correlated fading

Table 3 uses a `CorrelatedFading` model that forces both paths into the Bad
state simultaneously:

- Per-tick probability of starting a correlated burst: **2%**
- Burst duration: **10ms** (5 ticks)

When a correlated burst is active, `force_bad_state()` is called on both the
primary and secondary channel's GE models, overriding independent transitions.

## 2. What Each Table Measures

### Table 1: Backend Recovery vs Uniform Loss

Tests the five FEC backends (RaptorQ, Reed-Solomon, RLC window, Mettle window,
Streaming) under **uniform i.i.d. Bernoulli loss** at rates from 1% to 25%.

- Loss is applied independently per symbol (source + repair) using a seeded
  `ChaCha8Rng`.
- Block backends (RaptorQ, RS) split 2000 symbols into blocks of 200 and
  attempt per-block decode.
- Window backends stream symbols in batches of 10 with interleaved repair.
- The FEC rate controller sets the repair rate using a pre-warmed estimator
  at the target loss rate.
- Measures **recovery percentage** (fraction of source symbols decoded).
- Recovery is the only metric for Tables 1/1b since these are pure codec tests
  with no transport simulation.

Key question: "Which backend should I use at a given loss rate?"

### Table 1b: Backend Recovery vs GE Bursty Loss

Same structure as Table 1, but loss is generated by a GE channel with
`ge_for_target_loss(target, burst_len=3.0)` instead of uniform Bernoulli.

- Mean burst length is 3 packets (Bad state has 70% drop, Good state has 0%).
- Shows **burst sensitivity**: how much worse each backend performs when the
  same average loss rate is concentrated into bursts rather than spread
  uniformly.

Key question: "How sensitive is each backend to bursty loss?"

### Table 2: Wire Overhead Breakdown

Measures the wire-level cost of FEC across three scenarios (Datacenter at 0.1%
loss, WiFi at 2.5%, Congested at 12%). Uses RLC window mode with the adaptive
FEC rate controller (Realtime hint).

Overhead is broken into five layers:

| Layer            | What it counts                                      |
|------------------|-----------------------------------------------------|
| FEC repair       | Repair symbol payload bytes                         |
| Symbol padding   | Zero-padding when payload < symbol_size             |
| Per-symbol meta  | 25-byte bincode header per symbol (source + repair) |
| Batch/wire header| Per-batch framing overhead                          |
| Repair metadata  | Additional header bytes on repair symbols only      |

Key question: "How much bandwidth does FEC actually cost?"

### Matrix: Comprehensive FEC Comparison (replaces Tables 3/4/5)

A single unified matrix (ADR-0045) crossing four dimensions replaces the
former Tables 3, 4, and 5:

**Backends (6)**: RaptorQ, ReedSolomon, RLC, Mettle, Streaming, Retransmit

**Feature ablations (4)**: baseline, no_nack, no_reorder, no_pi

Retransmit only runs "baseline" (NACK/reorder/PI are FEC-specific).

**Paths (2)**: 1 path, 2 paths

**Scenarios (5)**:

| Scenario   | 1-path channels    | 2-path channels         |
|------------|-------------------|-------------------------|
| DC         | datacenter        | datacenter + datacenter |
| WiFi       | wifi_congested    | wifi_cong + wifi_cong   |
| LTE        | lte_congested     | lte_cong + lte_cong     |
| Satellite  | satellite         | satellite + satellite   |
| DC+LTE     | *(skip)*          | datacenter + lte_cong   |

DC+LTE only runs in 2-path mode (asymmetric scenario).

**Total**: 168 cells × 30 trials = 5,040 trial runs.

Three trial branches handle backend differences:

- **Window backends** (RLC, Mettle, Streaming): streaming encode/decode through
  SimChannel with adaptive FEC rate, NACK, reorder buffer, and PI feedback.
- **Block backends** (RaptorQ, RS): per-block encode, send individual symbols
  through SimChannel pipeline with multipath and reorder at symbol level,
  decode per-block. PI feedback adjusts repair rate across blocks.
- **Retransmit**: `ReliableSimChannel` (single or round-robin dual-path).
  No FEC overhead — only retransmission delay.

Metrics per cell (10, stable — never changes):

| Metric              | Description                                                |
|---------------------|------------------------------------------------------------|
| throughput_mbps     | (recovered symbols × symbol_size) / elapsed time           |
| recovery_rate       | Fraction of source symbols recovered (%)                   |
| overhead_pct        | FEC/retransmit overhead (%)                                |
| total_repair_count  | Absolute repair/retransmit symbol count                    |
| p50/p95/p99_latency | Latency percentiles (encode-to-deliver, ms)                |
| deadline_miss_pct   | Fraction arriving after 2× scenario base_delay (%)        |
| in_order_rate       | Fraction of consecutive deliveries in ascending order (%)  |
| tail_drops          | Packets dropped by bottleneck link queue                   |

All cells use **8% FEC budget** (MATRIX_FEC_OVERHEAD = 0.08).

Key questions answered by the matrix:
- "Which backend should I use for this scenario?"
- "Does each feature (NACK, reorder, PI) help?"
- "Is FEC worth the overhead vs retransmit?"
- "How much does multipath help?"

**Output files**: Each run writes timestamped markdown and JSON files to
`docs/benchmark-results-YYYY-MM-DD-HHMMSS.{md,json}` with git commit info.
Markdown shows means only; JSON includes full stats (mean/stddev/ci95).

## 3. Trial Structure

All tables use the same trial framework:

- **30 trials** per cell (`NUM_TRIALS = 30`)
- **Seed**: `trial * 137 + 42` (deterministic, reproducible)
- **95% confidence interval**: `mean +/- 1.96 * stddev / sqrt(n)` where
  `n = 30`. This is the standard normal approximation for a 95% CI.
- **Symbol count**: 2000 source symbols per trial (`NUM_SYMBOLS = 2000`)
- **Symbol size**: 1200 bytes (`SYMBOL_SIZE = 1200`)
- **Batch size**: 10 symbols per batch (`BATCH_SIZE = 10`)
- **Block size**: 200 symbols for block backends (RS requires `k + repair <= 255`)
- **Max FEC overhead**: 20% for Tables 1, 1b, 2; **8%** for the matrix

## 4. Simulation Model

### What is modeled

- **Propagation delay**: fixed per-channel base delay (1ms to 100ms)
- **Jitter**: uniform random [0, jitter_ms] added to each packet
- **Bursty loss**: Gilbert-Elliott two-state Markov chain with per-packet
  state transitions
- **Queuing and tail-drop**: `LinkModel` with finite buffer and serialization
  delay (congested variants only)
- **Multipath diversity**: source symbols sent on all available paths
  (redundant multipath)
- **NACK retransmission**: gap-based NACK generation from received sequence
  numbers, with repair symbol retransmission
- **Reorder buffer**: holds out-of-order symbols up to a configurable timeout
  before releasing them in sequence order
- **PI feedback controller**: proportional-integral feedback loop that adjusts
  FEC rate based on observed recovery success/failure

### What is NOT modeled

- **Real congestion control**: no AIMD, BBR, or CUBIC. Send rate is not
  throttled by congestion signals. The `LinkModel` tail-drop is the only
  backpressure mechanism.
- **Flow control**: no receive-window limits or credit-based flow control.
- **AQM**: no RED, CoDel, or ECN marking. Queues are pure FIFO with tail-drop.
- **Variable link capacity**: link speed is fixed for the entire trial. No
  bandwidth fluctuation, no competing flows.
- **Real TCP/QUIC stack**: `ReliableSimChannel` is a simplified model that
  re-enqueues dropped packets with a fixed retransmit delay. It does not
  implement slow start, congestion avoidance, or loss detection algorithms.
- **Application-layer framing**: no fragmentation, reassembly, or stream
  multiplexing. Each symbol is an independent unit.
- **Packet reordering from the network**: jitter can cause minor reordering,
  but there is no explicit reorder model (e.g., no out-of-order delivery from
  multi-path routing at the IP layer independent of the application).

## 5. Clock Resolution

The simulation uses a `MockClock` with **2ms ticks**:

```
let tick = Duration::from_millis(2);
```

Each batch of 10 symbols is processed over **5 ticks = 10ms**. This means:

- **Latency granularity**: all latency measurements are quantized to 2ms. A
  reported p99 of 10ms means "between 10ms and 12ms."
- **Reorder buffer timeout**: 25ms spans approximately 12.5 ticks. In practice,
  the reorder buffer flushes on the tick boundary after the timeout expires.
- **Correlated fading bursts**: a 10ms burst duration is exactly 5 ticks.
- **Jitter resolution**: uniform jitter (e.g., 0-3ms for WiFi) interacts with
  the 2ms tick. Packets scheduled for delivery between ticks are delivered on
  the next tick boundary.

The 2ms tick was chosen (reduced from an earlier 50ms) to provide reasonable
latency resolution without excessive simulation steps.

## 6. Estimator Pre-warming

### Loss estimator

Tables 1, 1b, 2, 4, and 5 use `make_estimator_for_loss(rate)`, which feeds
50 synthetic batches into the `LossEstimator` before the trial begins:

```rust
for _ in 0..50 {
    estimator.record_batch(1000, received);  // received = (1-loss)*1000
    estimator.record_rtt(Duration::from_millis(5));
    estimator.record_throughput(100_000_000.0);  // 100 MB/s
}
```

This ensures the estimator's Beta posterior has converged to the target loss
rate, so the FEC rate controller starts at a stable operating point from the
first batch. Without pre-warming, the Beta(1,1) prior takes 10-20 batches to
converge, adding noise to early batches.

### Table 3 estimator

Table 3 pre-warms the estimator to WiFi steady-state (2.5% loss) with 20
batches per path in the scheduler, plus explicit `record_batch(100, 98)` calls.

### PI controller

All tables that use the PI feedback loop pre-warm it with **10 feedback
cycles** (`fec_ctrl.feedback_update(true)` x 10) so the integral term starts
at a non-zero baseline. This prevents an initial undershoot in FEC rate that
would cause elevated loss in the first few batches.

## 7. Valid Conclusions and Caveats

### Strong conclusions

These results are robust to the simulation simplifications:

- **Backend ranking under both uniform and bursty loss**: the relative ordering
  of RaptorQ, RS, RLC, Mettle, and Streaming is a function of their codec
  properties (MDS vs near-MDS, block vs window), not congestion dynamics.
- **Overhead comparison**: wire overhead is a deterministic function of the FEC
  rate and header sizes. The simulation accurately counts bytes.
- **FEC vs retransmit latency direction**: FEC avoids the RTT retransmit
  penalty. This advantage holds regardless of congestion control details.
- **Multipath benefit**: path diversity reduces effective loss rate by
  spreading symbols across independent channels. This is a structural
  advantage independent of the transport protocol.

### Moderate conclusions

These results are directionally correct but the absolute numbers may shift
under more realistic conditions:

- **Absolute overhead numbers**: the FEC rate controller's Beta-posterior
  approach is conservative by design (95th percentile upper bound). Real
  overhead may differ with different estimator tuning.
- **Feature ablation deltas**: the relative impact of NACK, reorder, and PI
  depends on the loss rate and FEC budget. The 8% budget was chosen to
  maximize differentiation; at 20% budget, all features show near-zero deltas.
- **Congestion impact**: tail-drop queuing increases effective loss, but the
  lack of real congestion control means send rates are unrealistically high,
  which inflates queue occupancy.

### Cannot conclude

These questions require a more realistic simulation or real-world testing:

- **Real-world absolute performance**: without AIMD/BBR congestion control,
  the simulation cannot predict actual throughput or latency on real networks.
- **Cold-start behavior**: all tables use pre-warmed estimators. The learning
  phase from Beta(1,1) is not tested. (This is intentional -- cold-start is a
  separate concern from steady-state performance.)
- **Performance under variable capacity**: link speed is fixed. Bandwidth
  fluctuations, competing flows, and bufferbloat are not modeled.
- **Interaction with real protocol stacks**: the `ReliableSimChannel` is not
  QUIC or TCP. Results labeled "Retransmit" reflect a simplified retransmission
  model, not real protocol behavior.

## 8. How to Reproduce

Run the full benchmark suite:

```
cargo test --test bench_suite -p raptorpath --release -- --nocapture
```

This executes Tables 1/1b/2 and the comprehensive matrix sequentially.
Output is printed to stdout and written to timestamped files in `docs/`:
- `docs/benchmark-results-YYYY-MM-DD-HHMMSS.md` (human-readable)
- `docs/benchmark-results-YYYY-MM-DD-HHMMSS.json` (machine-readable)

Results are deterministic for a given code version: the `ChaCha8Rng` seeding
ensures identical random sequences across runs and platforms.
